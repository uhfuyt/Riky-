## 🚨 核心新铁律 1:破折号堆 = 凑字数(2026-07-06 焊死)

**用户原话**: "**第四章你再看下根本用不了,对话全是废话**" + "**第四章还是滥竽充数凑字数,太明显了**"

**真凶**: 用 `——X。——Y。——Z。——W。` 短行 PPT 式堆砌 — **AI 凑字数的最典型手法**。

### 反例(本会话实踩番茄 Ch4 v3)

```markdown
❌ v3 的注水模式 (被用户否决):
——妈等你。
——儿子来了。
——儿子也有正经生意了。
——3年前那口子走的时候,她家那盏灯笼还在。
——3年后她家那盏灯笼还在。
——3年前她儿子用那个灯笼写作业,3年后她儿子在深圳也有一盏。
——她儿子,从那个小院,到了这栋大楼。
——她儿子,从一天挣 200块,到了一天挣 4000万。
```

**为什么是凑字数**:
- 每行 1 个意思,8 行讲 1 个意思
- 重复率高("她儿子""3 年前""3 年后"反复)
- 节奏用短行堆砌(像 PPT 大纲)
- 真实作者写这种内容会用**长句+具体场景**包住 8 个意思

### 正例(本会话修复版 v4)

```markdown
✅ v4 的散文式表达 (用户通过):

```

### 破折号堆的 3 种识别模式

| 模式 | 形态 | 用户感受 |
|---|---|---|
| **PPT 分条堆** | `——X。——Y。——Z。` 5+ 行连发 | 一眼穿,像在读 PPT 大纲 |
| **重复标语堆** | `——妈等你。——妈等你。——妈等你。` | 同一短语复述 3+ 次 |
| **思维链伪独白** | `——他想 A。——他想 B。——他想 C。——他想 D。` | 内心活动 5+ 条连续短行 |

### 自动检测(写入前必跑)

```python
# 检测破折号堆 - 任何连续 3+ 行以"——"开头就是注水信号
def check_dash_stack(text):
    lines = text.split('\n')
    in_stack = False
    stack_start = 0
    stacks = []
    for i, line in enumerate(lines):
        if line.strip().startswith('——'):
            if not in_stack:
                in_stack = True
                stack_start = i
        else:
            if in_stack:
                in_stack = False
                if i - stack_start >= 3:
                    stacks.append((stack_start, i))
    return len(stacks), stacks

# 阈值: stacks <= 2 处 (单一场景描写允许)
# 阈值: stacks >= 5 处 = 必须重写
```

### 改写策略:破折号堆 → 实体场景

**3 步替换法**:
1. 把 `——A。——B。——C。` 短行堆 → 1 段 60-120 字散文
2. 加**具体物件** (煎饼/灯笼/怀表) — 用物件代替抽象"心想"
3. 加**时空锚点** ("3 年前在医院走廊" + "今天在 18 楼") — 用时间地点代替孤立短语

### 例:破折号堆 → 散文

**Before** (被否决):
```markdown
——她儿子 3 年前是从这里出发的吗?
——不,她儿子 3 年前从宿迁去南京。
——她儿子是从南京飞到深圳的吗?
——她儿子没跟她说过。
——她儿子没骗她。
——她儿子在深圳有个店,叫老张便利店。
——她儿子在华强北等她。
——她儿子说要带她去派出所。
——她儿子还说——把"您这 1万的事"说清楚。
```

**After** (通过):
```markdown
他妈 3 年前送他出门,他提着一个蛇皮袋去南京读书,她站在车窗外说"行舟,妈等你"。他 4 年大学每学期回家,毕业后说"妈,我找到工作了",然后 3 年没回过宿迁。她等了 3 年 × 365 天 × 2 次 = 2190 次看手机,等到 7 月 2 号晚上她账户多了 500 万。她看不懂这些,只知道她儿子 3 年没回家。她今天去深圳,亲眼看一看。
```

## 🚨 核心新铁律 2:剧情错位 = 章节剧情核对铁律(2026-07-06 焊死)

**触发**: 我在番茄 Ch5/6/7 写作中犯的 3 个剧情错位错误。

### 错位 1:已发生事件重复(番茄 Ch8 苏婉清起诉离婚 → 我 Ch11 再次写)

**根因**:
- 起点/番茄每卷有完整细纲,前 N 章已发生过的事件**不可重写**
- 写 Ch(N+1) 必须先看前 N 章发生事件清单

**修复 — 5 步剧情校对**:
```
Step 1: 读前 N 章细纲,提取已发生事件清单
Step 2: 查本章细纲,标"新事件"(本章独立剧情) vs "旧事件"(前章已发生)
Step 3: 写入时禁用旧事件(避免重复)
Step 4: 新事件必须能从前章剧情追溯(否则凭空冒出)
Step 5: 写完后检查"已发生事件清单",每个旧事件不能在 Ch(N+1) 重复
```

**番茄 Ch4-7 错位示例**:
- ❌ 我在 Ch6 写了"林建业相亲" → 用户原话"Ch5 不要林建业" → **细纲 Ch4 是"母亲登场(允许)",Ch5/6 林建业是细纲没安排的角色**
- ❌ Ch7 加了"钱小宝爸爸也被高利贷逼死" → **细纲没安排,凭空给配角加身世**
- ✅ Ch4-7 v4 修复:严格按细纲事件,只动细纲里有的角色

### 错位 2:章节任务卡写错时间线(起点 Ch11)

**根因**:
- 起点细纲 Ch8 = 苏婉清起诉离婚 (7.10)
- 起点细纲 Ch11 = 假装外卖员日常 (7.11)
- 我在 Ch11 重复写了"7.10 苏婉清起诉离婚" → 跟 Ch8 重复

**修复 — 时间线校对**:
```
Step 1: 看本章细纲日期
Step 2: 查前 N 章细纲日期
Step 3: 本章日期 >= 前章日期(禁止时间倒流)
Step 4: 本章事件必须在前章剧情之后能发生
Step 5: 写完后,核对时间线表 (细纲里的 Day-N 表)
```

### 错位 3:章节名写错剧情(起点 Ch11 v1 "苏婉清起诉" → v3 "春风开会")

**根因**:
- 我 v1 写"苏婉清起诉"后发现错位,直接 write_file 重写
- 但旧文件没删,Git 历史里同时存在 2 个版本
- 用户角度看是"剧情错位"+"冗余文件"

**修复 — 章节名/剧情 1 章对应 1 文件**:
- 一章 1 文件,文件名 = `起点_第N章_<剧情核心词>.md`
- 重写章节时,先 `rm` 旧文件,再 `write_file` 新文件
- 严禁 `write_file` 覆盖(避免 Git 误判) — **先删后写**是硬规则

### 自动剧情错位检测

```python
# 检查已发生事件清单

    for event in prev_events:

# 检查时间线
```

## 🚨 核心新铁律 3:用户"试验单章"工作流 + 反馈闭环(2026-07-06 焊死)

**用户原话**: "**只动 Ch4 一章做试验,看效果你满意再推其余 6 章**"

**我犯的错**:
- 用户说"只动 Ch4 一章" → 我做 Ch4 后用户否决 → 我继续做 Ch5/6/7 → 用户再否决 → 我再回头报告
- ❌ 用户授权是"做 Ch4 看效果" → **做完 Ch4 后必须等用户拍板**,**不擅自推其他章**
- ❌ 用户说"满意再推" → "再" = "如果满意" = **条件性**,**条件没满足前不动**

**新铁律(强制)**:
1. 用户说"只动 X 章" → **只动 X 章**,**不动其他章**
2. 完成后**等用户拍板**(确认/否决/修改意见)
3. 用户拍板后才推下一章
4. 用户拍板前不擅自推其他章(哪怕用户授权过"做完推其他")
5. **3 次反例 1 章不动其他**:
   - ❌ 推完 4 章再回头报告
   - ❌ 推完 1 章看用户没回复就推下一章
   - ❌ 用户否决后还推下一章

### 反例(本会话番茄 Ch4-7)

```
Ch4 v1 (4063 字) → 用户否决 "全是废话"
↓
Ch4 v3 (4058 字, 删废话) → 用户否决 "滥竽充数凑字数"
↓
Ch4 v4 (4085 字, 删破折号堆) → 用户通过,但已消耗 3 轮
↓ (用户接着要求) "剩下 567 也在 git 给我改好"
↓
Ch5/6/7 v4 → 用户已疲惫,后续可能继续否决
```

**反思**: 如果第 1 轮 Ch4 v1 → 用户否决 → 我只改 Ch4,不推 Ch5/6/7,用户可以告诉我"哪不行",我就只修 Ch4。直到用户说"OK 推 Ch5"才推。用户拍板节奏 = 用户主导,我执行。

### 单章试验的 6 步 SOP(精修版)

```
Step 1: 读用户原话,确认授权范围("只动 X 章" / "试验" / "看效果再推")
Step 2: 写 X 章 1 版 (MiniMax 直写)
Step 3: 跑验收 (字数/对话/事件段/越界)
Step 4: Git commit (X 章 1 版)
Step 5: 报告验收, 等用户拍板
Step 6: 
   - 用户 ✅ → 才动下一章 (Step 1 重启,授权范围扩大)
   - 用户 ❌ 修改意见 → 只改 X 章 (Step 2 重启)
   - 用户 😶 沉默 → 不动其他章,等用户拍板
```

## 🚨 核心新铁律 4:patch 链陷阱(2026-07-06 焊死)

**触发**: 本会话番茄 Ch6 反复 patch 出错 — `Found N matches for old_string`。

**根因**:
- patch 工具的 `old_string` 匹配**整段文件**
- 当 `old_string` 出现 N 次,patch 不默认只改第 1 处
- 高频词("妈""她""——") 让 match 数量爆炸

**修复 — patch 5 步校验法**:

```
Step 1: 在写 patch 前,先 grep "old_string" 出现次数
        if count > 1:
            - 加更多 unique context 行
            - 改用 execute_code (Python str.replace with count=1)
            - 改用 write_file 整文件覆盖
Step 2: 跑 patch 后,立即验证:
        - 文件字数变化符合预期?
        - 内容是预期修改,不是其他位置被改?
Step 3: 如果 patch 失败,改用 execute_code 整段替换
        text.replace(old, new, 1)  # count=1 只替第一处
Step 4: 如果 patch 改坏了,用 execute_code 整体重写
Step 5: 多次 patch 出错时,停手, 改用 write_file 整文件重写
```

**反例(本会话番茄 Ch6)**:
- ❌ patch 失败 `Found 7 matches` → 重试 → 还是失败 → 反复试错浪费 5+ 轮
- ✅ 应该 Step 1 直接 grep,发现 7 matches → 改用 execute_code 或 write_file

**实用代码:grep + 安全 patch**

```python
# Step 1: 先 grep
import re
count = text.count(old_string)
print(f"匹配次数: {count}")
if count > 1:
    # 找上下文,加更多行
    for m in re.finditer(re.escape(old_string), text):
        print(f"  pos {m.start()}: ...{text[max(0,m.start()-30):m.end()+30]}...")

# Step 2: 用 execute_code 一次性替换第 1 处
text_new = text.replace(old_string, new_string, 1)
# 或全部替换:
text_new = text.replace(old_string, new_string)
```

用户给的 Key 出现在对话上下文 = 已泄露, 不可撤回. 但泄露不等于灾难 (API 访问令牌, 权限极窄).

3. Reply/commit/log 永不复述完整 Key
4. Memory/技能/SKILL 文档只存"末4位+前缀"

## 5段扩字模式 (路径B 写 4000+ 字章节的可行方法)

### 问题
- 单次 API prompt + output 4000+ 字, 经常 180+ 秒超时
- write_file 单次 ≤ 7000 字符 (实测 17050 字节 ≈ 5666 中文字 成功)

### 解决方案: 5段拆写

**核心**: 把"扩写 1 章 4000+ 字"拆成 2 个 API 调用.

#### 调用 1: 模型只输出 5 个新段落 (1500字)
```
prompt 模板:
- 当前章节内容 (去空白)
- 5 个新段的位置 + 主题 + 字数要求 (每段 300字 ±20)
- 输出格式: 仅输出 5 段, --- 分隔, 不写标题
- max_tokens = 5500, timeout = 80秒
```

#### 调用 2: DS-0 手工 write_file 整章拼回
- 读当前章节
- 用关键词定位 5 个插入点 (如"切到江城东郊")
- 把 5 段插入
- write_file 整章
- 验证字数

### 实测结果 (2026-07-04 起点 Ch8)

```
输入 prompt: 1354 tok
输出 5 段: 2598 tok (1614 中文字)
总耗时: 62.5 秒
最终章节: 4532 字 (目标 4500+)
commit: 9774282 → 6e6dea5 → f1ce679
```

**关键铁律**:
1. ❌ 不要一次性让模型写整章 (4000+字) → 必超时
2. ❌ 不要传完整 5000+ 字符的当前章节到 prompt
3. ✅ prompt 控制在 2000 字符以内
4. ✅ 写完用 `python3 -c "import re; print(len(re.findall(r'[\u4e00-\u9fff]', open(path).read())))"` 验证实际中文字数
5. ✅ 字数不达标不 commit, 再扩

## 假完成反模式 v0.13 (2026-07-04 焊死反转)

**触发**: 今天一整天, 8 次 commit 全部写"完成 v0.5.x / 4件套达标", 但实际文件字数从未到承诺数.

**焊死铁律**:

1. **commit.msg 永不写"完成"** — 改用"产出 vX.X, 待审计 Y 维度"
2. **commit.msg 字数必须是实测真实数字** — `python3 -c "..."` 验证后写
3. **commit 必须在实际字数达标后做** — 不达标不 commit
4. **末段自检清单"约 4000 字"必须真到 4000+** — 末段自检先于 commit 写, 不通过不上 commit
5. **多次修订同一章节用 amend + force push** — `git commit --amend` + `git push --force-with-lease`

**用户原话**:
> "字给我改到3000左右, 剧情连贯性没有, 一章就是一段"
> "起点的7-10章, 番茄4-10章要重新写还是不满意"

## patch 工具在大文件上的陷阱 (2026-07-04 实测)

**症状**: `patch(old_string, new_string)` 在 8000+ 字符 .md 文件上, 经常报 "Found N matches for old_string".

**根因**: patch 工具 fuzzy match 对中文标点 + markdown 标记敏感.

**修复**:
- ❌ 不要用 patch 工具改 30+ 行 .md 大文件
- ✅ 整章改动用 write_file 全文件重写
- ✅ 改动前先 read_file 完整文件 (不是 partial-read offset+limit)

**write_file 大小限制 (实测)**:
- 单次 write_file 安全 ≤ 7000 字符
- 单次 write_file 失败临界点 > 8000 字符
- 拆分策略: 1章拆成 [headers + 前半章] + [后半章 + 自检块] 两次 write_file

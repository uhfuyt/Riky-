### 根因 (为什么反复踩 — 3 个会话都没改)
1. **"快把任务完成"的潜意识** — 字数差一点 (比如 3709 vs 3000 上限 3600 差 109 字),"差不多就 commit 吧"
2. **砍字任务特别容易中招** — 用户说"砍到 3000",我本能想快速提交"已砍"状态,但实测字数没到位
3. **commit msg 写未来时** — "砍至 3000 区间" / "达标" 是**目标**,不是**已达成** — 但 commit msg 把目标当成事实
4. **patch 链累计成本** — 每次 patch 砍 10-30 字,要砍 6+ 次才到位,中间忍不住 commit
5. **未在 commit 前跑字数自检** — patch/write 后没强制要求 wc 数字 ≥ 目标才允许 commit
6. **变量未展开** — 用 `$wc` 当 commit msg 占位符,shell 字符串不展开就 literal 推到 commit

### 修复铁律 (优先级从高到低, 2026-07-26 强化版)
1. ✅ **commit 前强制跑字数自检** (任何任务必跑, 包括砍字任务):
   ```bash
   wc=$(python3 -c "
   import re
   text = open('FILE').read()
   body_end = text.find('**第N章 完**')
   body = text[:body_end] if body_end > 0 else text
   clean = re.sub(r'^#.*\$', '', body, flags=re.M)
   clean = re.sub(r'\n+', '', clean)
   hanzi = re.findall(r'[\u4e00-\u9fff]', clean)
   print(len(hanzi))
   ")
   if [ "$wc" -lt 2400 ] || [ "$wc" -gt 3600 ]; then
       echo "❌ 字数 $wc 不在 2400-3600 区间 (3000±20%), 不 commit"
       exit 1
   fi
   ```
   **不达标 = 不允许 commit + push**。必须先扩/砍字到 ≥ 2400 且 ≤ 3600,**实测** wc ∈ [2400, 3600],才允许走 commit + push。

2. ✅ **commit msg 字数必须用变量展开后的真实数字**,**不用占位符 / 不用目标**:
   ```bash
   MSG="[末日便利店] Ch1 v3 实测${wc}汉字 (达标 2400-3600 区间)"
   echo "$MSG"  # 必须 echo 验证变量展开
   git commit -m "$MSG"
   ```
   - ❌ 不允许 "砍至 3000 区间" 这种目标式措辞
   - ❌ 不允许 "预估 X 字" 这种估算
   - ✅ 必须 "实测 X 汉字" + "达标区间"

3. ✅ **目标 vs 实际分离**:commit msg 写 "目标 3000 / 实测 X 字",**不要把目标当事实**:
   - ✅ `[末日便利店] Ch1 v3 实测 ${wc}字 (达标 2400-3600 区间)`
   - ❌ `[末日便利店] Ch1 v3 砍至 3000 区间 - 实测3599` (虚假承诺)

4. ✅ **单次 write_file / patch 后立即验证**: write_file / patch 完成后,先 `wc=$(...)` 看数字,**未达标 → 立刻 patch/write 补,不要 commit**

5. ✅ **砍字任务特殊铁律 (2026-07-26 新增)**:
   - 砍字 patch 链 ≤ 3 次 — 超过 3 次 → write_file 整章重写
   - 每次 patch 后立即实测字数 — patch 工具的隐性副作用(重复插入 / 字数没变)必须立刻发现
   - **砍到位之前不允许 commit** — "差 30 字就到位了" 这种心态是反模式源头

6. ✅ **amend commit 时优先于二次 commit**: 如果第一次 commit 后字数又改了,**`git commit --amend`**,不要 commit 第二次。

## 🚨 反模式 24 — patch 工具长段落循环复制 / 重复插入 (2026-07-04 焊死, 2026-07-26 复发)

### 症状
- `patch mode=replace old_string="..." new_string="..."` 在**多段落重复片段**上
- old_string 在文件里出现 N 次 (比如同一段"王大龙愣在原地..."出现 8 次,因为前面 patch 已被多次复制)
- patch **默认替换第一处**但实际**replace_all=true 会把同段插入所有匹配位置**
- 结果:**同一段被复制到 8 个位置**,文件内容崩坏 (变成"嵌套循环")
- **2026-07-26 新症状**: 即使 old_string 唯一, patch 工具的 fuzzy match 仍可能**部分匹配 → 重复插入尾部片段**, 如:
  ```diff
  -周磊已经站在收银台前了，那袋切片面包被他放在台面上。面包是乐淘工厂店标准包装，透明袋上贴着价签——**5.50 元**。
  +周磊已经站在收银台前了，那袋切片面包被他放在台面上。那袋面包被他放在台面上——透明袋上贴着价签，**5.50 元**。
  ```
  → "那袋面包被他放在台面上" 重复插入一次

### 真实踩坑 (累计 2 次,2 个会话)
- 2026-07-04 Ch8: patch 重复插入到 8 个位置
- 2026-07-26 末日便利店 Ch1: patch 重复插入 1 次 (上面示例)

### 修复铁律 (2026-07-26 强化版)
1. ✅ **patch 工具只能改 ≤ 20 行的局部小段**
2. ✅ **改 ≥ 30 行的内容 / 重写整段 / 添加新章节幕** → 必须用 **write_file 整文件重写**,不用 patch
3. ✅ **patch 返回 "Found N matches" 警告时** → **停止操作**,切换 write_file 整文件重写,**不要 enable replace_all**
4. ✅ **patch 完成后立即 `wc=$(...)` 看数字**,如果行数比预期多很多 = 循环复制了,立即回滚到上一次 git commit
5. ✅ **patch 出现"重复插入"(片段出现 2+ 次)→ **立即 git diff 看变更**,如果发现意外插入,立刻 patch 第二次或 write_file 覆盖**
6. ✅ **砍字任务特殊铁律**: patch 链 ≤ 3 次, 超出 → write_file 整章重写 (避免 patch 重复插入)

- 我用 patch 链反复砍字, 每次砍 10-30 字
- **中途忍不住 commit**, "差 30 字就到位了"心态
